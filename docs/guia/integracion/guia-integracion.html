Descripción del servicio

Voracious es un servicio para vigilar el apetito de riesgo multivariado de portafolios financieros. El integrador envía series de indicadores de riesgo (por ejemplo, LCR, NSFR, VaR o concentración) y el servicio devuelve una carta de control que indica cuándo el comportamiento conjunto de esos indicadores se aparta de lo habitual, aunque cada indicador por separado parezca normal.

La carta T²MRCD

La carta calcula, para cada observación, un estadístico T²: la distancia de Mahalanobis al cuadrado respecto a una ubicación y una dispersión estimadas con MRCD (Minimum Regularized Covariance Determinant; Boudt, Rousseeuw, Vanduffel y Verdonck, 2020). La implementación es un port fiel de rrcov::CovMrcd de R. Frente a las cartas clásicas (Shewhart, EWMA, Hotelling), MRCD:

  • no supone que los datos sigan una distribución normal;
  • resiste valores atípicos y el enmascaramiento (atípicos que esconden a otros);
  • funciona con más variables que observaciones (p > n) gracias a la regularización.

Una observación genera una señal cuando su T² supera estrictamente el límite operativo de la versión vigente del modelo.

Ciclo de vida del modelo

El servicio es dueño del ciclo de vida de la carta; el integrador solo consulta y solicita:

  • Versiones inmutables. La versión 0 nace con la Fase I. Cada recalibración produce una versión nueva en estado propuesta, que solo rige cuando un aprobador la aprueba. Una versión no se modifica: solo cambia su estado (proposed, active, superseded, rejected).
  • Límite operativo por régimen. La versión 0 vigila con el límite de Fase I (provisional y fijo); las versiones recalibradas, con el de Fase II.
  • No retroactividad. Una versión aprobada rige desde effective_from, que debe ser posterior a la última observación puntuada. Cada observación se evalúa con la versión vigente en su fecha.
  • Anotaciones. Las señales se anotan con su causa asignable (sí o no), cuál fue y la acción tomada.
  • Recalibración. Por defecto amplía la base (EXTEND): la base vigente más las observaciones nuevas, salvo las que una persona marcó con causa asignable. Solo reemplaza la base (REPLACE) si se pide explícitamente (force_replace) o si hay un evento estructural sin resolver (por ejemplo, una fusión).
Nota sobre la tasa de falsas alarmas

El nivel nominal de los límites es 0,5 %. Como el bootstrap remuestrea solo el 75 % central del histórico (para que una contaminación no detectada no infle el límite), la tasa real de falsas alarmas medida frente a observaciones en control es de ≈ 2,3 % con el límite de Fase I y ≈ 2,1 % con el de Fase II (media entre semillas, entre ~1 % y 3,8 %; n = 200, p = 3). Es una característica del diseño, no un error. El caso p > n no está medido.

Arquitectura

Despliegue

El servicio corre en un único servidor con Docker Compose: api (FastAPI sobre uvicorn, un solo proceso), postgres 17 (sin puertos publicados), migrate (aplica las migraciones y termina) y backup (volcado diario, siete días). La API solo escucha en 127.0.0.1:8000; el integrador llega a ella por un túnel SSH. Los secretos viven cifrados (SOPS y age) y se montan como Compose secrets. La cola de trabajos vive dentro del proceso de la API: un reinicio interrumpe los trabajos en curso, que quedan failed con el código JOB_INTERRUPTED y deben volver a pedirse.

Capas

El código sigue una arquitectura hexagonal. La capa API traduce HTTP, verifica el token y aplica la matriz de roles; la capa de aplicación orquesta los casos de uso (pasos de Fase I, puntuación, ciclo de vida); el dominio contiene la carta T²MRCD y el estimador MRCD, sin dependencias de red ni de base de datos; la infraestructura implementa la persistencia, el almacenamiento de datasets y la cola. La cola reparte los trabajos en carriles por coste (estimación, calibración, ligero y orquestación), de modo que un bootstrap de minutos no retrasa una puntuación de milisegundos.

Acceso y autenticación

Acceso de red

La API no está expuesta a internet: escucha en 127.0.0.1:8000 del servidor, sin HTTPS propio. El integrador abre un túnel SSH (cifrado) con la cuenta que le entrega el operador de Voracious y usa la API como si fuera local:

# Terminal 1: túnel hacia la API del servidor (se mantiene abierto)
ssh -N -L 8000:127.0.0.1:8000 <usuario>@<servidor>

# Terminal 2: variables que usan todos los ejemplos de esta guía
export BASE=http://127.0.0.1:8000
export C=$BASE/v1/charts/t2mrcd

Se recomienda que el operador entregue una cuenta solo de túnel: sin consola, sin copia de ficheros y con el reenvío limitado al puerto de la API. Para ello antepone estas opciones a la llave pública del integrador en el authorized_keys de esa cuenta y le asigna como shell de inicio /usr/sbin/nologin, que no permite entrar:

restrict,port-forwarding,permitopen="127.0.0.1:8000" ssh-ed25519 AAAA… integrador

Con esa cuenta funciona el túnel de arriba (ssh -N) y se rechaza cualquier otro uso de SSH: una consola, un comando remoto o un reenvío hacia otro destino.

Obtención de un token

Toda ruta de negocio exige la cabecera Authorization: Bearer <token>. El token es un JWT firmado. El operador de Voracious emite el token en el servidor y lo entrega al integrador por un canal seguro; el integrador no necesita ni debe tener acceso a la llave de firma ni al servidor (la cuenta de túnel de Acceso de red solo reenvía el puerto de la API).

Para cada persona o sistema que vaya a llamar a la API, el integrador pide al operador un token con estos datos:

El integrador recibe el token (una cadena de tres partes en base64url separadas por puntos, que empieza por eyJ) y su fecha de caducidad (claim exp). Un token sirve solo para el tenant y los roles con que se emitió: para aprobar versiones hace falta otro token con el rol approver (en los ejemplos, $APPROVER). Para usarlo, se guarda en una variable de entorno sin escribirlo en disco ni dejarlo en el historial del shell:

# Pegar el token y pulsar Intro (no se muestra en pantalla)
read -rs TOKEN

Cuidado con los tokens
  • No compartirlos. Cada persona o sistema usa su propio token: su sub queda registrado como autor de lo que hace.
  • No ponerlos en la URL. La API solo lee el token de la cabecera Authorization (uno en la query se ignora) y una URL acaba en registros e historiales.
  • Renovarlos al caducar. Antes de exp se pide otro al operador; un token caducado responde 401 con expired. Ante la sospecha de que un token se filtró, se avisa al operador.

Caducidad y renovación

Un token vale 8 horas por defecto y 7 días como máximo: el operador no puede emitir tokens de vida mayor y la API rechaza cualquier token con exp − iat mayor (lifetime_too_long). La API admite 30 segundos de margen de reloj en exp, nbf e iat. No hay revocación individual: un token deja de valer al caducar o cuando el operador rota la llave de firma. El integrador debe pedir un token nuevo antes de exp y no reutilizar tokens de larga vida.

Errores 403

Con un token válido cuyos roles no permiten la operación, la API responde 403 FORBIDDEN con los roles admitidos en details.required_roles. Ejemplo real: un token con solo approver intenta subir un dataset.

KO 403

{
  "code": "FORBIDDEN",
  "message": "los roles del token no permiten esta operación",
  "details": {
    "required_roles": ["admin", "analyst"]
  }
}
Nota

En las rutas con cuerpo JSON, el rol se comprueba después de decodificar el JSON y antes de validarlo contra el esquema: un JSON sintácticamente inválido responde 422 aunque el rol no baste; un JSON válido que no cumple el esquema responde 403 si el rol no basta. POST /v1/datasets, que admite también CSV y multipart, comprueba el rol antes de leer el cuerpo: con un rol insuficiente responde 403 sea cual sea el cuerpo. La autenticación (401) ocurre siempre antes de leer nada.

Aislamiento por tenant

El tenant de cada petición es el claim tenant del token; el integrador no puede elegir otro. Un recurso de otro tenant responde exactamente igual que uno inexistente (404), de modo que no se puede averiguar si existe. Ejemplo real: el token de banco-b consulta un dataset de banco-a.

Sondeo

El servicio no ofrece notificaciones: el integrador sondea. Se recomienda un intervalo según el paso, con un tiempo máximo de espera y retroceso si el trabajo tarda:

# Espera a que un recurso llegue a un estado final (requiere curl y jq).
# Uso: esperar URL [intervalo en s] [máximo en s]
# Sale con 0 y el estado final; 1 si la respuesta no se arregla esperando
# (401, 403, 404…, o un cuerpo sin status); 2 si se agota el tiempo máximo.
esperar() {
  url=$1; intervalo=${2:-5}; limite=$(( $(date +%s) + ${3:-900} ))
  cuerpo=$(mktemp)
  while [ "$(date +%s)" -lt "$limite" ]; do
    codigo=$(curl -s -o "$cuerpo" -w '%{http_code}' "$url" \
      -H "Authorization: Bearer $TOKEN")
    case "$codigo" in
      200)
        estado=$(jq -r '.status // "sin_status"' "$cuerpo" 2>/dev/null)
        case "$estado" in
          succeeded|failed|cancelled)
            echo "$estado"; rm -f "$cuerpo"; return 0 ;;
          queued|running) ;;
          *) echo "respuesta inesperada: ${estado:-no es JSON}" >&2
             rm -f "$cuerpo"; return 1 ;;
        esac ;;
      000|5??) ;;  # sin conexión o servidor no disponible: se reintenta
      *) echo "HTTP $codigo $(jq -r '.code // empty' "$cuerpo" 2>/dev/null)" >&2
         rm -f "$cuerpo"; return 1 ;;
    esac
    sleep "$intervalo"
  done
  echo "tiempo máximo agotado" >&2; rm -f "$cuerpo"; return 2
}
esperar "$C/limits/$LIMITS_ID" 10 1200

Encadenamiento por identificador

Cada paso es un recurso independiente que recibe los identificadores de los pasos anteriores, no los datos. El integrador puede detenerse en cualquier paso, revisar su resultado y continuar. La tubería /pipelines/phase1 encadena los mismos pasos y produce el mismo modelo, bit a bit.

dataset_id ──▶ [ /exclusions ] ──▶ /fits ──▶ /limits ──▶ /models ──▶ model_id
                output_dataset_id   fit_id    limits_id
model_id ──▶ …/scores ──▶ …/observations ──▶ …/annotations
model_id ──▶ …/recalibrations ──▶ /exclusions ──▶ …/extension

Los pasos validan la coherencia de la cadena antes de encolar: unos límites que no son del ajuste indicado (LIMITS_FIT_MISMATCH), un paso que no pertenece a la recalibración (RECALIBRATION_MISMATCH) o un paso aún no terminado (FIT_NOT_READY, LIMITS_NOT_READY) se rechazan de inmediato.

Idempotencia y reintentos

La API no admite todavía una cabecera de idempotencia. Antes de repetir un POST tras un corte de red, el integrador debe comprobar si el recurso ya se creó. El comportamiento de cada operación ante un reintento es:

OperaciónEfecto de repetirla
POST /v1/datasetsCrea otro dataset con otro dataset_id y el mismo content_hash.
/fits, /limits,
/exclusions, /models,
/pipelines/phase1		Crea otro trabajo; con los mismos parámetros y semilla el resultado es idéntico.
…/scoresRegistra las observaciones otra vez (duplicadas). No se debe reintentar sin comprobar.
…/annotationsAñade otra anotación (son de solo adición; vale la más reciente).
…/recalibrationsSeguro: con una recalibración en curso responde 409 RECALIBRATION_IN_PROGRESS.
…/recalibrations/{rid}/extensionIdempotente: devuelve la misma extensión.
…/approve, …/rejectSeguro: la segunda vez responde 409 VERSION_NOT_PROPOSED.
Trabajo con JOB_INTERRUPTEDEl servicio se reinició durante el trabajo: se vuelve a pedir el mismo paso.

Recalibración

Una recalibración recalcula todo (ajuste MRCD y límites) sobre una base nueva y termina en una versión propuesta. Se hace por pasos (mode: "stepwise") o en una llamada (mode: "pipeline", por defecto). Las cadenas de pasos son:

DecisiónCadena
EXTEND (por defecto)abrir → [exclusión desde anotaciones] → /extension → /fits → /limits → …/versions
REPLACE (forzado o por evento)abrir → [exclusión desde anotaciones] → /fits → /limits → …/versions

Buenas prácticas y límites

Tiempos de cálculo orientativos

CasoTiempo
Fase I completa, 200 × 300, B = 100, servidor de 2 vCPU≈ 6 min (una calibración bootstrap medida: 5,5 min; memoria pico 245 MB)

Puntuación de un loteMilisegundos
Recalibración completa; caso p > nSin medir. EXTEND hace una calibración sobre la base ampliada: se puede estimar como una Fase I de ese tamaño.

El coste crece con B, con n y, sobre todo, con p. Los trabajos largos no bloquean las puntuaciones (carriles separados), pero dos calibraciones simultáneas se ejecutan una detrás de otra.

Sondeo y reintentos

  • Sondear con el intervalo de la tabla de Sondeo y un tiempo máximo; aumentar el intervalo si el trabajo tarda (retroceso exponencial hasta 60 s).
  • Decidir por code, nunca por message.
  • No reintentar a ciegas un POST de puntuación tras un corte: comprobar antes con …/observations si las observaciones ya se registraron.
  • Reintentar los errores 5xx y los trabajos JOB_INTERRUPTED; no reintentar los 4xx sin corregir la petición.
  • Fijar y guardar la semilla (seed): con la misma semilla y los mismos datos el resultado es idéntico.
  • Cancelar las recalibraciones paso a paso abandonadas: mientras sigan abiertas, bloquean otras recalibraciones del modelo.

Datos

  • Enviar siempre variables y observed_at: dan trazabilidad y permiten detectar columnas cambiadas de orden (VARIABLES_MISMATCH).
  • Usar fechas con zona horaria y en orden; una recalibración selecciona las observaciones por observed_at.
  • No enviar valores ausentes ni infinitos: se rechazan. Imputar o descartar antes de subir.
  • Anotar todas las señales investigadas; solo las anotadas con causa asignable salen de la base.

Tokens

  • No exponer tokens: nunca en la URL, en registros, en el historial del shell ni en repositorios. Guardarlos en una variable de entorno o en un gestor de secretos.
  • Pedir tokens con el menor rol y la menor vida necesarios; renovarlos antes de exp.
  • Pedir tokens distintos para quien opera (analyst) y quien aprueba (approver).
  • Ante la sospecha de un token filtrado, avisar al operador: la única revocación es rotar la llave de firma.

Pre-lanzamiento

Durante la fase de pre-lanzamiento hubo cambios que rompen el contrato dentro de la v1 (OpenAPI 0.1.0): rutas, campos y códigos que se eliminaron o cambiaron sin cambiar de versión. Se marcan abajo con Rompe el contrato. A partir de la primera versión publicada, la API se versionará: un cambio incompatible llegará con una versión nueva y se anunciará en estas notas.

2026-10-20 · Autenticación con JWT y roles Rompe el contrato

  • JWT obligatorio (Authorization: Bearer, EdDSA) con los roles analyst, approver y admin y su matriz de permisos. Códigos 401 UNAUTHENTICATED (12 motivos) y 403 FORBIDDEN. Vida máxima del token: 7 días.
  • El tenant sale del token: la cabecera X-Tenant-ID desaparece (si llega, se ignora; sin token, 401) y TENANT_REQUIRED sale del catálogo.
  • actor sale de los cuerpos de anotaciones, eventos estructurales, aprobación, rechazo y recalibración: enviarlo da 422. El actor es el sub del token.

2026-10-14 · Recalibración que amplía la base por defecto Rompe el contrato

  • La recalibración amplía la base por defecto (EXTEND) y solo la reemplaza con force_replace o con un evento estructural sin resolver. Nuevo paso síncrono …/recalibrations/{rid}/extension, obligatorio en EXTEND antes del ajuste; GET …/recalibrations/{rid} expone kept_dataset_id y extension_dataset_id. Justificaciones initial_fit, default_extend, forced_replace y structural_event.
  • Desaparece /comparisons, junto con los códigos RECALIBRATION_DECISION_PENDING, COMPARISON_NOT_FOUND y COMPARISON_NOT_READY. Los informes de recalibración anteriores no son compatibles.

2026-10-09 · Persistencia en Postgres, nombres de variables y fechas

  • El estado se guarda en Postgres y sobrevive a los reinicios; un trabajo interrumpido por un reinicio queda failed con JOB_INTERRUPTED.
